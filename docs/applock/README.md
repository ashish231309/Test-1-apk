# App Lock detection architecture (Stage 7)

This document records the Stage 7 detection boundary. It does not claim that Stage 7 can block an app: the overlay and authentication presentation are Stage 8 work.

## Protected application identity and persistence

- `ProtectedApplication` contains only a validated `packageName`; labels, icons, activity names, list positions, and process IDs are not identities.
- Persisting the protected set is necessary so the detector can resume its policy after process death. The one application-private `SharedPreferences` file `nivara_protected_applications` contains a format version and a deterministic newline-delimited set of package identifiers. It contains no labels, usage events, credentials, keys, or session data.
- A single `SharedPreferences.Editor.commit()` writes the version and complete encoded set atomically. One application-scoped repository serializes read/modify/write updates with a `Mutex`. The Stage 9 settings UI must use this same `ProtectedApplicationRepository`; it should restart/re-evaluate monitoring after a configuration change.
- First install (neither preferences file nor SharedPreferences backup exists) is an intentionally empty configuration. An existing file or interrupted-commit backup with a missing/unknown version, missing payload, malformed package line, or XML/read error is `Unavailable`; it is never converted to an empty set. A failed update commit returns `UNAVAILABLE` and does not report the change as successful; `commit()` preserves the previous complete configuration atomically. The service reports degraded configuration state and emits no `NoProtectionRequired` decision. **If the entire private preferences file is deleted, that is indistinguishable from first install and the protected set becomes empty; this loses the prior protection configuration. Clearing Nivara's app data has the same effect.** Because the whole-file-missing case is necessarily treated as first-run, a deleted file can therefore remove all protection rather than produce a corruption state. This is the documented consequence of choosing a single minimal preferences file; Stage 9 should clearly surface this reset consequence to the user.
- Missing or disabled packages are not automatically deleted from configuration. Usage-event matching is by package name only and will not crash if a configured package never appears in the current event stream.

## Foreground detection and permission states

- `AndroidForegroundApplicationDetector` uses `UsageStatsManager.queryEvents()` (API 21+, above Nivara's API 28 minimum). It maps `ACTIVITY_RESUMED` / legacy `MOVE_TO_FOREGROUND`, pause/stop/background events, `SCREEN_NON_INTERACTIVE`, and `KEYGUARD_SHOWN` into Android-free event records. The domain reducer orders each new batch by event timestamp, ignores malformed package identities, tracks only the current candidate, and treats a pause for another package as irrelevant.
- The detector makes a five-minute bounded startup lookback, then queries with a one-second overlap from the previous successful query time. A bounded 512-key in-memory dedup set avoids replaying overlap events. No usage-event history is retained beyond the current query batch, logged, or persisted. An initial window with no usable foreground baseline is `FOREGROUND_DETECTION_UNAVAILABLE`, not `NoForeground`; the detector keeps its cursor and can recover when a later activity event arrives. After process death, if the five-minute startup window has no baseline (for example, an app has remained open longer than the window), detection stays degraded until a new activity event arrives rather than guessing which app is foreground.
- A two-second polling interval is centralized in `AppLockMonitoringPolicy`; the degraded retry interval is ten seconds. Polling is used because UsageEvents is a query API, not a subscription/callback API. This is not a real-time guarantee. When Usage Access is missing, the platform query returns no usable data, or a protected-app snapshot is corrupt, the monitor exposes an explicit degraded state and does not call the result an empty foreground or empty protected set.
- The monitor checks the existing `UsageAccessRepository` before reading events on each poll. `NOT_GRANTED` and `UNAVAILABLE` are distinct degraded states. If access is revoked during monitoring, the FGS remains visibly degraded and checks again at the slower interval; it does not silently become safe. Android may return `null` from `queryEvents()` while the user is locked; that is also degraded until a usable event baseline is available.
- Event batches may include launcher, Settings, system UI, or transient packages. The detector does not auto-protect any of them. Only an exact match with the explicitly persisted protected-package set can require authentication. Stage 9's picker should source choices from Stage 6's launcher-only `ApplicationRepository`, and should avoid automatically selecting system packages. Nivara's own package (including build variants) is injected from `Context.packageName` into the pure decision layer and always maps to `NoProtectionRequired`.

## Decision, events, and session authority

- `ProtectionDecider` is pure: no foreground, Nivara itself, an unprotected package, or a currently authenticated Stage 5 session yields `NoProtectionRequired`; a protected package with the manager-reported unauthenticated state yields `AuthenticationRequired(packageName)`.
- Each evaluation reads `SessionManager.currentState()`, which performs Stage 5 expiry checks. There is no App Lock unlocked boolean, per-package session, credential cache, last-unlock timer, or second `lockNow()`. The manager's existing timeout and Quick Lock transitions therefore affect the next poll directly.
- `AuthenticationRequestDebouncer` emits one `ProtectionEvent.AuthenticationRequired` per continuous unauthenticated visit to a protected package. It suppresses repeated emissions while the prompt is pending; a non-protected/no-foreground observation resets the marker. A manager-authenticated observation also resets it, so a later expiry or Quick Lock can request authentication again. Failed/cancelled authentication does not affect credential or biometric attempt counters; Stage 8 remains responsible for presenting the existing authentication flows.
- The event `SharedFlow` is not the only handoff: `AppLockDetectionState.Monitoring` also exposes the current pure decision and pending package so a later Stage 8 observer can recover current state if it subscribes after an event. Neither path launches UI.

## Monitoring lifecycle and foreground service

- Continuous checks must continue while another app is on screen. A WorkManager/job schedule is too inexact for this use; Stage 7 therefore uses one user-visible Android foreground service, `AppLockDetectionService`, with the `specialUse` type because Android has no narrower standard type for user-selected app-use protection monitoring. Android's type/subtype and Google Play declaration are subject to platform/store review; this implementation does not claim Play approval.
- The manifest adds only `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE` for this service and declares the `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` explanation. The service is non-exported and has a persistent low-importance notification with a Stop action. It is started by the application-scoped controller from Nivara's resumed, user-visible Activity, only when Usage Access is granted and the protected set is non-empty. Controller outcomes for missing access, unavailable config, empty config, and start restrictions are distinct.
- Android 13's `POST_NOTIFICATIONS` runtime permission is not declared/requested: Android documentation says it is not required to launch an FGS, although the FGS notification is still mandatory. If the user denies ordinary notifications, Android may show the FGS notice only in Task Manager rather than the notification drawer. The notification contains no protected package name.
- One `NivaraContainer`-owned monitor is shared with the service. Repeated service starts call an idempotent `start()` and do not create parallel polling loops. Explicit controller/notification stop cancels that loop; `onDestroy()` resets event/debounce state. The notification Stop action stops the current service run; a later Nivara Activity resume rechecks prerequisites and may start monitoring again. `START_STICKY` allows Android to recreate the started service after process death; a new process has a new, unauthenticated Stage 5 session and loads the persisted package set. No boot receiver, accessibility service, alarm, OEM auto-start, or battery exemption is added. Detection after reboot resumes when the user next opens Nivara; user force-stop and OEM process-management behavior are not guaranteed around.
- The application controller checks prerequisites before `startForegroundService()`. Android 12+ background-start restrictions are surfaced as `START_UNAVAILABLE`; it does not attempt a background-start workaround. Removing the final protected package stops the service. Process/service destruction cancels transient state; no phantom in-memory monitor survives.

## Overlay, privacy, and platform limitations

- **No overlay permission is added in Stage 7.** Detection can expose an internal `AuthenticationRequired` event without UI. Stage 8 must decide and implement overlay capability, Settings entry, presentation, and authentication handoff. Detection alone does not block the target application.
- No `SYSTEM_ALERT_WINDOW`, `POST_NOTIFICATIONS`, battery-optimization exemption, accessibility service, storage/media, location, camera, or microphone permission is added. The FGS permissions are the only Stage 7 additions; their exact justification is above. Existing Usage Access remains the user-granted prerequisite declared in Stage 6.
- Production code does not log, transmit, or persist foreground packages or usage events. The only persistent new security configuration is the protected package identifier set. No usage statistics/history feature is introduced.
- Android's UsageEvents timing, multi-window behavior, user/device-lock transitions, permission availability, process reclamation, FGS restrictions, and OEM policies can vary. The two-second poll is an intended cadence, not a guarantee. Physical-device/emulator verification is outstanding; unit tests of event mapping/decisions are not proof Android reports a particular foreground package.
