# Stage 14 — File Import, Encryption & Vault Index

Stage 14 extends, rather than replaces, the Stage 13 root/metadata/key lifecycle and Stage 2 crypto services. `VaultRepository`, `VaultStorage`, `SafVaultStorage`, `AndroidVaultLocationStore`, `VaultMetadataCodec`, `AuthenticatedEncryption`, `KeyWrappingService`, `DeviceKeyStore`, `SecureRandomSource`, `Aes256Key`, and `CryptoContext` remain the authoritative boundaries. `DefaultVaultRepository` is the single scoped bridge to the already-unwrapped Stage 13 vault content key. It validates the existing wrapped key and authenticated header before each content operation, clears temporary raw bytes, and never returns a key handle or bytes through the domain/UI API.

## Android-free item model and index

`VaultItem` stores a 128-bit random `VaultItemId`, original display filename, optional MIME type, observed plaintext size, import timestamp, object format/size, and an encrypted per-item data-key envelope. Index validation rejects blank/path-like/control-containing names, malformed MIME values, negative sizes/timestamps, duplicate IDs, oversized records, malformed UTF-8, and unsupported object versions. The filename is display metadata only; object names are always `<lowercase-hex-item-id>.nvc`.

`VaultIndexCodec` produces a canonical binary representation sorted by item ID. It is explicitly versioned, bound to the vault ID and generation, rejects duplicate rows, truncated fields and trailing data, and bounds index input at 8 MiB/20,000 records. The `NVIX` file frame is separately versioned and length-delimited. The complete plaintext index is encrypted and authenticated with the existing Stage 2 `AuthenticatedEncryption`, the dedicated `nivara.vault.content-index.v1` purpose, and AAD containing the vault ID and generation. It does not reuse the Stage 13 metadata/header context.

The index contract distinguishes **Missing**, **Ready-empty**, **Ready-populated**, **Corrupt**, **UnsupportedVersion**, **Unavailable**, **AccessDenied**, **ObjectsWithoutIndex**, and **VaultUnavailable**. No parse, permission, crypto, provider, or version failure is converted into an empty list. The highest committed generation is authoritative: a corrupt latest generation is not bypassed by silently loading an older generation. Unknown/orphan object files are never scanned to reconstruct rows.

## Per-item content format and key/nonce strategy

Each `.nvc` object begins with a fixed 35-byte header: magic `NVCO`, format version 1, AES-256-GCM algorithm identifier, the 16-byte internal item ID, nonce-length marker, and a fresh 12-byte GCM nonce. The remainder is ciphertext followed by the 16-byte GCM tag. The complete header and vault/item binding are authenticated as GCM AAD under the dedicated `nivara.vault.content-object.v1` context. Object ID/header mismatch, malformed/truncated streams, wrong tags, wrong recorded lengths, and unsupported versions are rejected before indexing.

A fresh 256-bit random per-item data key is created inside the scoped crypto operation and encrypted under the existing vault content key with the existing Stage 2 `AuthenticatedEncryption` service and dedicated `nivara.vault.item-key.wrap.v1` AAD binding (vault ID + item ID). Only this encrypted key envelope is placed in the encrypted index record; the vault key is not copied into every row. The per-item key is used for one GCM encryption of that item's object, with a fresh 96-bit nonce from `SecureRandomSource`; decryption during read-back validation reuses the object's stored nonce as required by GCM. Re-imports receive a new random item ID and key. No new KDF, AES implementation, Keystore wrapper, or credential-derived key path is added. Stage 2's existing random-nonce envelope implementation remains responsible for the vault-key-encrypted index and wrapped item-key records.

## Bounded-memory streaming

The only new Stage 2 primitive is `StreamingAuthenticatedEncryption`, implemented by the existing `JcaAesGcmEncryption`. It applies the same AES/GCM/NoPadding, AAD, and tag semantics as the existing record API and processes 64 KiB chunks. Import, encryption, output, read-back size validation, and object authentication never call `readBytes`, `readAllBytes`, or hold an arbitrary source file in a `ByteArray`. Cancellation, I/O failure, checkpoint failure, or tag failure aborts the stream and closes/clears working buffers. Decrypt output is quarantined/discarded until `doFinal()` validates the tag; it is not published as plaintext.

## SAF picker and import transaction

Source selection uses `ACTION_OPEN_DOCUMENT` with one openable document. No broad storage permission or persistent source grant is requested. The Android `Uri` is kept only in a one-shot in-memory data-layer registry mapped to a random `VaultSourceSelectionId`; it is not returned to Compose/domain contracts, saved state, preferences, logs, or the vault index. The selected vault root URI, one-shot source URI, and generated encrypted object ID remain separate.

Before reading the document, the import use case rechecks the existing `SessionManager`, validates provider display name/MIME/optional size, confirms a Ready authenticated index, generates an independent stable item ID, and checks for collision. The source is opened read-only. Nothing renames, deletes, writes, or otherwise modifies the source. The pipeline streams into a unique `.pending-<item-id>-<random>` document under `data/objects/`, checks authorization throughout, closes the stream, compares measured lengths, requires provider rename support, and renames to the deterministic internal-ID `.nvc` name. It then opens and decrypts/authenticates the finalized object to a discard sink and checks tag, object ID, plaintext length, and stored object length. Only after those checks and one final authorization checkpoint does the repository atomically add a row to a new authenticated index generation.

If the session expires while streaming, the incomplete temporary output is removed only if the SAF provider allows exact temporary cleanup; it is never indexed. If expiry/cancellation/provider failure occurs after object rename but before the index commit point, the finalized object remains an unindexed orphan. The index adapter checks authorization immediately before renaming a fully written index generation; that rename is the commit point. Expiry after that point cannot safely roll back a committed generation, so the import remains committed while the UI clears authenticated item state when the existing session expires. If the index commit fails before the commit point, the finalized object remains an unindexed orphan. Such objects are not counted as items, reconstructed from a directory scan, automatically deleted, or silently treated as a valid empty item.

## Atomicity, recovery and serialization

Index snapshots are immutable files named `index-<20-digit-generation>.vxi`. Every update writes a unique same-directory pending document, closes it, reads it back byte-for-byte, checks provider rename support, renames to a previously unused generation name, and reads back the final document. Previous committed snapshots are not overwritten or pruned. A failed index commit therefore does not replace the prior valid snapshot; if final verification of a newly created snapshot fails, cleanup targets only that new snapshot. A provider's rename is not assumed to be a universal filesystem transaction or `fsync` guarantee.

The import coordinator serializes imports; the index repository serializes index initialization/updates; SAF storage serializes its own document operations; and the Stage 13 repository's scoped content-key operation serializes against its vault operations. This is process-local only, not a cross-process or provider-wide lock. No startup scan repairs the index. This import-layer contract does not perform delete/restore/trash; current reversible Trash/Restore behavior and its limits are described in the [vault guide](README.md).

The SAF adapter now permits only `data/index/` and `data/objects/` as direct content folders so Stage 13 inspections continue to recognize the same populated vault root. It does not interpret their content as metadata or alter the selected root/key hierarchy. SAF rename/read-back support is provider-dependent; lack of rename capability is an explicit write failure rather than a copy/delete fallback.

## UI and deferred scope

The existing vault route adds a single-file picker action, initialization of an explicitly empty authenticated index, progress/status feedback, and a simple authenticated filename list/count. UI state carries only domain-safe selection tokens and item metadata—never a `Uri`, path, source bytes, credentials, or keys. The existing camouflage, launcher, App Lock, hidden/protected application repositories, navigation, credential/biometric flow, and session manager are unchanged. Media grouping, photo/video/audio viewers, search, albums, sorting, thumbnails, trash, restore, and reinstallation/recovery are excluded. Stage 15 may add media-specific photo/video/audio/document vault presentation; Stage 18 remains responsible for defining recovery/reinstallation before portability can be claimed.

## Limits and verification

The index is bounded to 8 MiB and 20,000 rows; SAF index/object directory listings are bounded at 25,000 entries, and the implementation does not prune old index snapshots. Finalized orphan objects consume part of the bounded object-directory allowance. The provider must support directory creation, stream read/write, rename, and read-back for the same tree. The adapter performs extra sequential read-back/authentication passes, so large-document import may be slow on cloud-backed providers. This design cannot promise power-loss durability beyond SAF's reported operations. Per-item random keys/nonces rely on `SecureRandomSource`; Android/JCA provider behavior and SAF implementations require device testing.

JVM coverage is added for deterministic/bounded index codecs, ID/filename validation, streamed GCM round trips and tampering/truncation/checkpoints, scoped content-key/index/object integration, index corruption/write failures, session-expiry outcomes, source immutability, and finalized-but-unindexed orphans. Instrumented tests exercise Android's JCA provider with multi-megabyte streams and random nonce samples. Their addition is not proof of execution: the README and completion report record actual tool/device results separately. Static verifier rules and individually mutated negative fixtures cover forbidden alternate crypto, broad permissions, source URI leakage, whole-file materialization, missing index authentication, non-atomic writes, weak session gating, and scope creep.
