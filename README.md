# Nivara

Nivara is a native Android privacy and security workspace with one primary PIN, password, or pattern, optional AndroidX biometric authentication, and one process-memory session with an absolute timeout and Quick Lock. Stages 6–9 provide shared launchable-app discovery and App Lock configuration, detection, and secure authentication. Stage 10 adds a durable hidden-app preference; Stage 11 adds a selectable Android Home activity, Nivara home surface, and app drawer that omits hidden applications. Hidden apps remain installed and functional in Android and other launchers. A normal, explicit authenticated reveal is temporary and session-bound. Nivara does not automatically become the default Home application. Stage 12 uses one fixed, presentation-only “Home” identity and a documented ordinary recovery entry; it does not change the Android package identity or hide Nivara from the system.

## Custom launcher and Android Home selection

Nivara offers a standard Android Home activity and app drawer using the existing `ApplicationRepository` and `HiddenApplicationRepository`. Hidden applications are omitted from Nivara's normal drawer only; they remain installed and launchable elsewhere. If hidden-state storage cannot be confirmed, Nivara displays no drawer entries rather than exposing an unknown hidden app. An explicit **Show hidden apps for this session** action uses the existing `SessionManager`; Quick Lock, session expiry, or process recreation clears the temporary reveal. App Lock remains independently configured and monitored.

To try Nivara as Home, choose it manually through Android's normal Home settings (**Settings → Apps → Default apps → Home app** on many devices; wording varies by Android version and device maker). Nivara does not change the default automatically. The Home activity and app selection have not been runtime-verified on a device/emulator in this change. Search is intentionally omitted from the initial drawer; it can later reuse the existing `InstalledApplicationSearch` contract.

Stage 12 — App Identity Camouflage & Recovery Entry — presents a fixed “Home” label and neutral home icon. Open the ordinary “Home” app-drawer entry to reach Nivara’s existing authentication/settings flow even when another Home app is selected; when Nivara is Home, its Home screen also offers “Nivara settings”. See [camouflage and recovery](docs/camouflage/README.md). This is presentation only: the Android package remains `com.ashishkumar.nivara`, installed-app visibility is unchanged, and this is not invisibility or a security boundary.

## External encrypted vault — Stages 13–17

Stage 13 establishes one authenticated vault root in a user-selected Android Storage Access Framework folder. Stage 14 adds single-document SAF file import, bounded-memory AES-GCM object encryption, per-item random keys, and an authenticated versioned index in that same root, reusing Stage 2 crypto and Stage 13 key lifecycle. Stage 15 adds an authenticated-metadata item list and bounded in-memory previews for supported images and strict UTF-8 plain text, with non-mutating missing/unindexed/unfinished diagnostics and explicit per-item errors. Stage 16 adds encrypted album metadata, Unicode-aware metadata-only search, deterministic sorting, and explicit stale item-reference handling. Stage 17 adds reversible Trash/Restore state to the authenticated item index: encrypted objects remain in place, item IDs and metadata remain stable, and album references become effective again on restore. There is no empty-trash, permanent deletion, secure erase, or automatic expiry. New imports persist a plaintext SHA-256 digest inside the existing authenticated index metadata; legacy rows decode as Active with no digest, and trash never rescans them. Albums persist only stable item IDs; the authenticated index remains authoritative for item metadata. Active collections exclude trashed items, and Trash has its own searchable/sortable, restore-only surface; all active collections reuse the same Stage 15 viewer path with bounded image/text previews. MIME category recognition does not imply a viewer: PDF, audio/video, other documents, and generic files remain unsupported; no plaintext file cache or seekable media staging is used. The existing navigation graph and single `SessionManager` remain in place. The vault never selects a fallback folder, requests a broad storage/media permission, or modifies source documents. Reconnect the exact tree if access is lost; the current Android Keystore wrapper is installation-bound, so reinstall recovery is not implemented. Sharing/export, backup, cloud, and recovery remain out of scope. Stage 17 semantics and limitations are documented in [vault storage and limitations](docs/vault/README.md) and [Stage 17](docs/vault/stage17.md), alongside [Stage 16](docs/vault/stage16.md), [Stage 14](docs/vault/stage14.md), and [Stage 15](docs/vault/stage15.md). Android compilation and runtime support must not be inferred from source presence; check the testing status below.

## Technology

- Kotlin and native Android
- Jetpack Compose with Material 3
- AndroidX Navigation Compose, Lifecycle ViewModel, BiometricPrompt, Preferences DataStore, and foreground-service support
- Kotlin Coroutines for off-main-thread key derivation and platform discovery
- Gradle Kotlin DSL with a version catalog
- Minimum Android version: Android 9 (API 28)

## Build and test

Install JDK 17 and Android SDK Platform 35, then configure the Android SDK path in your local environment or Android Studio. From the project root, use the Gradle wrapper:

```sh
./gradlew testDebugUnitTest assembleDebug assembleAndroidTest assembleRelease lint
python3 tools/verify_nivara.py
python3 -m unittest tools/test_verify_vault_organization.py tools/test_verify_vault_trash.py
```

The debug APK is written to `app/build/outputs/apk/debug/`. Run `./gradlew connectedDebugAndroidTest` on an API 28+ device or emulator for PackageManager discovery/icons, repository storage, Android Keystore, biometric availability, the launcher Home-intent contract, the SAF picker and vault-navigation contracts, and vault state/session-gate Compose tests. The launcher instrumented contract tests check that the Home component resolves and that the separate app-drawer recovery component resolves to `MainActivity`; they do not select Nivara as the user's default Home or prove OEM behavior. The app intentionally omits drawer search in this stage and retains the shared name ordering. JVM test sources cover Stage 9 management, Stage 10 hidden state, Stage 11 filtering/reveal/session/fail-closed behavior, Stage 13 vault metadata/initialization, Stage 14 index codecs, streaming crypto, import checkpoints, authenticated item-key use, corruption, and orphan behavior, plus Stage 15 MIME classification, fake-session viewer cleanup, authenticated quarantine/tamper behavior, and index inventory diagnostics. Stage 16 adds album model/codec, Unicode search, sorting, stale-reference, authorization, persistence/readback/corruption/crash-consistency, and ViewModel-facing state tests. Stage 17 adds v1/v2 index-codec, digest/import, lifecycle transitions/readback, authorization/concurrency, album preservation, active/Trash search/sort, and ViewModel state tests plus Android instrumented codec-contract sources. Instrumented tests require a connected device/emulator to execute; no device runtime is inferred from source presence. The real `UsageStatsManager.queryEvents()` smoke test runs only when Usage Access is already granted; it does not grant permission or assume a foreground package. Home-app selection, real Android Home resolution, external application launching, icon rendering in the drawer, activity lifecycle, session expiry, Quick Lock, TalkBack, Usage Access UX, overlay behavior, and interactive biometric authentication still require device/emulator verification. Run `python3 tools/verify_nivara.py` and `python3 -m unittest tools/test_verify_hidden_architecture.py tools/test_verify_launcher_architecture.py tools/test_verify_camouflage_architecture.py tools/test_verify_vault_architecture.py tools/test_verify_vault_organization.py tools/test_verify_vault_trash.py` for static and negative architecture checks. Open the root directory in Android Studio to sync and run the app on a device or emulator.

## Security foundation

Core cryptography, credential verification, session boundaries, persistence, and App Lock architecture are documented in [SECURITY.md](SECURITY.md) and [docs/applock/README.md](docs/applock/README.md). Stage 10 hidden-state policy is in [docs/apphide/README.md](docs/apphide/README.md), and the launcher lifecycle/Home contract is in [docs/launcher/README.md](docs/launcher/README.md). The app stores a separate package-only hidden preference; temporary reveal exists only in the launcher ViewModel's memory and uses the existing `SessionManager`. The launcher does not log or transmit package names, persist reveal state, disable applications, or hide them from Android or other launchers. Overlay protection still requires the user-granted `SYSTEM_ALERT_WINDOW` capability and remains subject to Android background-execution and OEM limitations; it is not a platform-enforced kiosk. Stage 12's fixed “Home” identity and recovery route are presentation-level only; the package remains discoverable and removable through Android, and no security or privacy boundary is created.

## Project structure

The single `app` module keeps the project lightweight. Compose UI, navigation, and theme live under `ui`; security, credential, and Android-free vault/content contracts and codecs are in `domain`; JCA, Android Keystore, DataStore, and SAF document/source adapters are in `data`; and `di` wires the shared services through the application container. The selected vault tree contains versioned metadata plus generated encrypted-object, authenticated-index, and encrypted-organization-metadata directories after explicit initialization. Trash is a lifecycle field inside authenticated index rows, not a second database or storage directory. UI code depends on domain service boundaries rather than platform storage classes.
