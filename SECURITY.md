# Security model and implementation notes

This document describes Nivara's credential, biometric, process-memory session, App Lock, launcher, vault, recovery, and cryptographic boundaries. It records implementation contracts and limitations; it is not a claim of an independent penetration test, formal verification, or device-specific security certification. The actual Android/OEM, SAF-provider, Keystore, biometric, overlay, and process-lifecycle environment remains part of the threat model.

## Cryptographic formats and APIs

- Payload encryption is AES-256-GCM with a 128-bit tag and a 96-bit nonce. The `NIVR` binary envelope uses version 1 and algorithm ID 1; its length-prefixed ciphertext contains the JCA-produced tag, so the tag is not duplicated. Parsers reject unknown versions/algorithms, invalid lengths, and truncated input.
- Each encryption gets a fresh nonce from the JCA `SecureRandom` source for ordinary AES keys. AndroidKeyStore keys keep randomized encryption enabled and use the platform provider-generated IV. GCM's 96-bit random nonces have a negligible but non-zero collision probability; future high-volume/per-key use must retain this bound or introduce durable, concurrency-safe nonce allocation before raising usage limits.
- The envelope's version and algorithm identifier, a domain separator, caller-supplied purpose and binding bytes are authenticated as AAD. Callers must supply the same non-secret context when decrypting. No low-level purpose is inferred from UI state.
- Wrapped keys have a separate `NVKW` versioned container, which identifies credential-derived, recovery, or AndroidKeyStore protection. The protection type, purpose and binding are also bound into the inner GCM authentication. The intended design is a random 256-bit content key protected by independent wrapping keys; no user credential is treated as a vault/content key.
- Credential derivation is PBKDF2-HMAC-SHA-256, parameter version 1, 600,000 iterations, a unique 16-byte generated salt, and 32-byte output. The suspend API performs derivation on `Dispatchers.Default`. Callers own returned derived bytes and must clear them when no longer needed; only non-secret KDF parameters and salt should be retained for later derivation.

## Credential enrollment and verification

- A single Preferences DataStore record is active at a time. It is stored under `noBackupFilesDir` and contains the selected method, credential-record/KDF versions, PBKDF2 parameters, salt, base64-encoded authenticated wrapped-verifier envelope, and only the minimum primary failed-attempt count/throttle deadline. There is no primary-credential removal/reset API.
- Enrollment derives with the existing `CredentialKeyDeriver`, wraps a freshly generated 32-byte random verifier under the derived AES-256 key using the existing key-wrapping/AES-GCM services, and stores only that ciphertext envelope. Verification succeeds only when the GCM authentication tag validates; the unwrapped verifier is never returned to UI and is cleared. Credential-type ID is bound into the authenticated context. This creates an offline-guessing target if the private DataStore file is extracted; PBKDF2 slows guesses but cannot add entropy to a short PIN.
- PINs are 6–12 ASCII digits and the enrollment rules reject repeating groups up to three digits and simple ascending/descending sequences. Passwords are 10–128 characters with no arbitrary composition requirement; empty/whitespace-only and control-containing values are rejected. Pattern canonical form is lowercase ASCII hex of `[format-version=1, point-count, ordered zero-based 3x3 cell IDs]`; skipped midpoint cells on straight segments are inserted before KDF input so drawing the same path normalizes consistently. The canonical form and all raw inputs remain transient.
- Failed attempts are persisted without credential history. The fourth consecutive failure starts exponential temporary delays (1, 2, 4, 8, 16, then capped at 30 seconds); successful verification or credential replacement resets the count. There is no permanent lockout. This is a local throttling foundation, not a hardware-enforced boundary: copied/modified local storage can reset or roll back the count, and offline guessing is unaffected. The persisted deadline uses wall time, so device clock changes can affect the temporary delay; later policy should consider stronger device-bound state if the threat model requires it.
- Credential screens use password transformation/password semantics, a secure-window flag, non-saveable Compose state, and clear drafts after submission/navigation. The app does not access the clipboard or log/save the values; platform text-edit context-menu and IME behavior is not claimed to be fully suppressed. Compose text inputs necessarily hold transient `String` values internally, and JVM/provider memory copies prevent guaranteed erasure as described below.

## Biometric authentication and lockout

- AndroidX `BiometricPrompt` is the only biometric UI/API. Availability comes from `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)`. The prompt accepts strong biometrics only; Android's negative action asks the user to switch to Nivara's primary PIN/password/pattern flow. There are no custom sensor APIs, matching, or biometric templates in Nivara.
- Setup and disable are gated by successful authentication through the existing `PrimaryCredentialService`. The application refuses biometric authentication unless the single primary credential is configured. Disable removes the app's biometric key and state; biometric enablement never replaces/deletes the primary record.
- A dedicated AES-256-GCM Android Keystore key is non-exportable, requires per-operation user authentication (`AUTH_BIOMETRIC_STRONG` on API 30+, per-operation authorization on API 28–29), and is invalidated when biometric enrollment changes. `BiometricPrompt.CryptoObject` carries a cipher using that key. The successful operation encrypts a fresh ephemeral random challenge and discards/clears the output; the key is not used as a content/encryption key and no raw key or challenge is persisted. The alias is a fixed, non-secret identifier, not key material.
- Only `disabled`/`enabled`/`invalidated` state and a separate biometric failed-attempt count/deadline are stored in another no-backup Preferences DataStore. If key use reports permanent invalidation or the alias is missing, state becomes `invalidated`, biometric authentication stops, and the primary credential remains available. Recreating a key happens only after an explicit, primary-authenticated enable action.
- Nivara's application policy permits four unmatched biometric callbacks without a delay. The fifth failed match cancels the current prompt and starts a 30-second local delay. After the delay, a further failed match starts another 30-second delay; a biometric success or successful primary authentication resets this separate counter. This state is device-local and wall-clock-based, so it is a policy foundation, not tamper-proof anti-rollback protection.
- Android's `ERROR_LOCKOUT` and `ERROR_LOCKOUT_PERMANENT` are surfaced as **system lockout**, not Nivara lockout. Android/hardware lockout is authoritative and is never cleared, bypassed, or counteracted by regenerating a key. `BiometricManager`/prompt errors for no hardware, unavailable hardware, no enrollment, unsupported configurations, and required security updates are mapped to unavailable states. A negative-button request, user cancellation, match failure, app delay, system lockout, and platform error remain distinct outcomes.
- A failed biometric attempt never calls the primary credential service and does not increment its PBKDF2 failure counter. The explicit primary fallback uses the existing primary authentication service; failure affects only the primary counter, while success resets the separate biometric counter. Biometric verification returns only typed authentication outcomes; the application session is owned separately by `SessionManager`.

## In-memory sessions and Quick Lock

- `DefaultSessionManager` is the single process-scoped session authority, supplied once by `NivaraContainer`. Its `StateFlow` starts as `Unauthenticated`; only successful existing primary or biometric outcomes create an immutable session recording `PRIMARY` or `BIOMETRIC` and monotonic start/expiry times. It retains no credential type, credential, derived key, biometric key, token, or authentication result.
- The default policy is a five-minute **absolute** session lifetime from successful authentication. Normal activity does not refresh the deadline. The exact deadline is expired (`now >= expiresAt`); access checks synchronously clear an expired session, and a process-scope timer emits `Unauthenticated` so observing UI updates without waiting for another user action. Timeout configuration is a domain value, not UI arithmetic.
- The shared `TimeProvider` retains wall time for the existing persisted primary/biometric attempt deadlines and provides a separate monotonic elapsed-realtime clock for sessions. Android's implementation uses `SystemClock.elapsedRealtime()` for session timing, so wall-clock changes cannot extend or shorten a session. Session timing never reads or modifies either attempt tracker.
- `lockNow()` clears the in-memory session and invalidates authentication attempts that were already in flight. A late result from a prompt started before Quick Lock cannot restore access; a new primary or biometric authentication must complete afterward. Quick Lock and timeout do not change credential records, biometric enrollment/key state, or either attempt counter.
- Session state is held only in the application's process-scoped manager. It is not put in Compose saved state, `SavedStateHandle`, Preferences/DataStore, files, databases, or encrypted storage. A newly created manager (including after process recreation) is unauthenticated. There is no persistent unlocked flag or session token.
- `mayAccessSensitiveContent()` is the shared gate used by sensitive App Lock and vault operations; it does not replace repository-level rechecks. Sensitive credential, App Lock, launcher reveal, and vault screens retain their existing secure-window/lifecycle handling. Recovery only reconnects an existing vault key and never creates or restores a session.

## App discovery and Usage Access preparation

- The setup screen queries only activities matching Android's `ACTION_MAIN` + `CATEGORY_LAUNCHER` signature. Manifest package visibility is narrowed to that launcher intent; Nivara does not request `QUERY_ALL_PACKAGES`, enumerate installed-package internals, launch discovered apps, persist the inventory, log it, or send it over a network. Labels are resolved defensively with package-name fallback; duplicate launcher activities collapse to one package identity, Nivara is excluded, and a package that disappears or fails during snapshot construction is skipped. Discovery is an in-memory snapshot refreshed when the setup screen loads and again when it resumes.
- `InstalledApplication.packageName` is the stable identity; display labels are not identifiers. Domain ordering is deterministic and case-insensitive by label and package name, with an exact package-name final tie-breaker, and the Android-free search helper matches normalized labels or package names. These are preparation data contracts, not an app-selection or enforcement policy.
- Usage Access is represented as `GRANTED`, `NOT_GRANTED`, or `UNAVAILABLE`. The Android repository checks `AppOpsManager.OPSTR_GET_USAGE_STATS` and treats only `MODE_ALLOWED` as granted; a missing platform service or an AppOps failure is unavailable. The discovery screen does not call UsageStatsManager query methods or collect usage history. `PACKAGE_USAGE_STATS` is declared because App Lock detection requires usage observation and the platform treats access as a user-controlled special capability: declaration expresses the use, while the user grants or revokes it in the official Settings screen. It is not requested with a runtime permission dialog.
- The Settings action uses `Settings.ACTION_USAGE_ACCESS_SETTINGS`, handles launch failure without crashing, and the screen re-reads status on `ON_RESUME`; returning from Settings is not assumed to mean access was granted. The setup status and app list remain in ViewModel memory only.
- **Overlay permission is separate from Usage Access.** The discovery/status screen does not use `SYSTEM_ALERT_WINDOW`; the secure Nivara-owned App Lock surface declares it, with an independent capability check and Settings flow. No battery-optimization exemption, OEM workaround, or usage-history feature is added.
- The preparation screen itself does not require authentication: it reads launchable-app/capability state and offers the system Settings handoff, but does not select protected targets, change lock policy, or establish an unlocked session. This keeps prerequisite setup available before enforcement exists and does not create an alternate unlock authority. Any future protected configuration/action must gate through the existing `SessionManager` and use its `lockNow()` behavior; The discovery screen creates no session, credential cache, or unlocked flag.
- The screen uses the shared `SecureScreenEffect` as required by the existing UI security boundary. That does not imply App Lock protection is active.
- Platform references: [Package visibility declarations](https://developer.android.com/training/package-visibility/declaring), [UsageStatsManager](https://developer.android.com/reference/android/app/usage/UsageStatsManager), [PACKAGE_USAGE_STATS](https://developer.android.com/reference/android/Manifest.permission#PACKAGE_USAGE_STATS), [AppOpsManager](https://developer.android.com/reference/android/app/AppOpsManager), and [Settings.ACTION_USAGE_ACCESS_SETTINGS](https://developer.android.com/reference/android/provider/Settings#ACTION_USAGE_ACCESS_SETTINGS).

## App Lock detection and service

- Protected applications have one stable identity: package name. The selected set is persisted separately from the in-memory session in an application-private, versioned SharedPreferences file. Package-only updates are written atomically. Malformed or version-unknown contents produce an explicit unavailable/degraded state, never a successful empty set. As documented in [docs/applock/README.md](docs/applock/README.md), complete deletion of the preferences file is indistinguishable from first install and resets the set to empty; this deliberately documented data-loss case removes prior protection configuration.
- A pure domain reducer/decision layer receives package-only foreground observations, the persisted protected set, the injected Nivara package name, and `SessionManager.currentState()`. It creates no Activity, overlay, biometric prompt, credential attempt, or authentication cache. A small per-visit event debouncer prevents repeated authentication-required emissions while an unauthenticated protected package remains active; leaving it resets the marker.
- Android detection incrementally queries UsageEvents on a centralized two-second cadence and retains only bounded in-memory event deduplication/current-package state. It does not persist or log usage history. Missing Usage Access, unknown/corrupt protected configuration, a failed query, and a missing initial foreground baseline remain explicit degraded states and are not interpreted as an empty protected set or safe foreground.
- A single NivaraContainer-owned coordinator is run by a non-exported `specialUse` foreground service with a visible notification and explicit Stop action. The service can be restarted by Android after process death, but background detection, event timeliness, OEM behavior, and store-policy acceptance are not guaranteed. The service uses its notification as the user-visible rationale and does not request `POST_NOTIFICATIONS`.
- The only App Lock service permissions are `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE`, required for the declared Android foreground-service type. `PACKAGE_USAGE_STATS` remains the user-granted Usage Access prerequisite. No overlay, notification-runtime, accessibility, or battery-optimization permission is declared for detection. The overlay owns authentication presentation; the monitor produces only decisions/events. Detailed service, polling, persistence, corruption, and limitation decisions live in `docs/applock/README.md`.

## Secure App Lock presentation and authentication

- The overlay adds only `SYSTEM_ALERT_WINDOW` and uses `TYPE_APPLICATION_OVERLAY` with `FLAG_SECURE`. A separate capability contract preserves granted, not granted, unavailable, and Settings-launch failure distinctly. Neither permission failure nor Usage Access failure is treated as an empty protected set. The minimal setup screen exposes both prerequisites independently.
- `AndroidAppLockPresentationController` consumes monitor state; the detector remains free of WindowManager/UI/authentication duties. It checks the exact package identity against protected configuration and a fresh launcher snapshot, rechecks the live foreground and overlay capability, and checks the existing `SessionManager` before display and auth commit. Request IDs are transient process-memory identities, not Intent extras or storage.
- PIN/password/pattern authentication uses `PrimaryCredentialService` followed by `SessionManager.authenticatePrimary`; biometric authentication uses the existing `BiometricAuthenticator` followed by `SessionManager.authenticateBiometric`. There is no per-package session, duplicate credential/biometric verification, App Lock counter, timer, or unlocked-package persistence. Success creates only the ordinary global session; timeout and `lockNow()` behavior remain unchanged.
- Duplicate/stale results are ignored; a late success racing request invalidation is immediately revoked with the existing `SessionManager.lockNow()` safeguard. Back does not dismiss a still-valid overlay, outside touches are not passed through, and home/recents clear the old request when the detected foreground changes. Return to Nivara discards that transient request without marking its target unlocked.
- Primary input arrays and view text are cleared on submit/cleanup. The overlay and its biometric Activity use secure windows; the latter is non-exported and excluded from Recents. There are no package/credential logs, sensitive Activity extras, accessibility APIs/services, or App Lock-specific authentication state in storage. `FLAG_SECURE` is not a guarantee against external cameras, privileged/compromised systems, or every OEM capture surface.
- This remains best-effort app-level protection. Android background Activity-start rules, UsageEvents cadence, process death/force-stop, overlay revocation, multi-window/system UI, and OEM power management can interrupt or delay enforcement. The overlay does not add an FGS or notification solely for its presentation and does not rely on the overlay grant to start an FGS. Android 15's overlay-related FGS restrictions and current device behavior require runtime testing. No emulator/device verification is claimed here.

## Key and secret handling

- AndroidKeyStore aliases are namespaced and validated. Keys are AES-256, GCM-only, no-padding, encrypt/decrypt keys with randomized encryption enabled. Key bytes are not exported. Hardware-backed storage depends on the device/provider and is not guaranteed by this implementation.
- Credential storage creates only a fresh random verifier for local credential checking. The Preferences DataStore stores only credential metadata, the wrapped verifier, and attempt state described above—not raw credentials, derived keys, plaintext verifier bytes, vault content keys, or recovery material. Vault key wrappers remain in the vault-specific stores described in [the vault guide](docs/vault/README.md).
- Mutable temporary buffers under application control are cleared where practical. JVM providers, `SecretKeySpec`, `Cipher`, JIT compilation, garbage collection, and platform internals may make additional copies that cannot be reliably overwritten. Therefore this implementation does not claim perfect memory erasure. Avoid converting secrets to `String`, keep their lifetime short, and clear caller-owned password/key arrays after use.
- Security exceptions expose stable generic messages and intentionally omit provider exceptions and sensitive values. Security code does not log key, password, PIN, derived-key, or recovery material.

## Integrated security boundaries

- Exactly one local primary credential is active: PIN, password, or pattern. Biometric authentication remains optional and secondary. Credential changes require the old credential and do not change the separate vault content key or recovery wrapper.
- App Lock uses one protected-application repository, the existing UsageEvents-based detector, a user-granted overlay, existing primary/biometric authentication, and the sole `SessionManager`. It creates no per-package unlocked state. Detection is best-effort and subject to Android/OEM lifecycle and background-execution behavior.
- Nivara's launcher uses the existing launchable-app catalogue and hidden-app repository. Unknown hidden state fails closed. A temporary reveal is explicit, in-memory, tied to the live authenticated session, and cleared on session loss/process recreation. “Hidden” means omitted from Nivara's drawer only; Android and other launchers can still expose the installed app.
- The external vault is SAF-only and has one random 256-bit content key. The local installation wrapper uses Android Keystore; the optional recovery wrapper protects the same key and does not derive from the primary credential, location, device ID, or a server. Per-item keys are wrapped under the existing content key. Recovery requires normal local enrollment/authentication and explicit reselection of the exact tree after reinstall.
- Recovery records and versioned vault metadata/index/organization records are authenticated and bounded. Failed, unsupported, incomplete, or unavailable storage is not treated as empty, repaired, silently adopted, or replaced. SAF readback/rename and app-process mutexes do not provide a portable provider `fsync` or cross-process transaction guarantee; consult [the vault guide](docs/vault/README.md) for the documented persistence limits.
- Encrypted objects use authenticated streaming AES-GCM; item lists and organization views use authenticated metadata only. The current viewer supports bounded in-memory image and strict UTF-8 plain-text previews. Unsupported media/PDF types are not opened, and no whole-file plaintext cache or temporary plaintext file is part of the viewer path.
- `FLAG_SECURE`, transient buffer clearing, local attempt throttles, and Android Keystore are useful defense-in-depth but are not guarantees against a compromised OS, rooted device, external camera, all provider/OEM failure modes, offline extraction/guessing, or every JVM/provider memory copy. There is no cloud/account/server, telemetry, or remote recovery service.
